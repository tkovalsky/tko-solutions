## The problem

Health plans rarely miss a mandate because nobody read it. They miss it because the mandate has to cross too many organizational boundaries before it becomes real.

Policy is interpreted. Requirements are documented. Technology work starts. Each team reports progress. But leadership still cannot answer the questions that determine whether the organization is actually ready:

- Which obligation changes which operational behavior?
- Which workflows, systems, interfaces, vendors, controls, and exceptions are affected?
- Who is accountable for each open gap and decision?
- What evidence would substantiate readiness tomorrow—not simply support a green status report?

The risk sits in the translation layer between policy and implementation. That is where implicit assumptions, local workarounds, vendor dependencies, state variation, and downstream effects remain invisible until testing, launch, or escalation.

## The Regulatory Implementation Readiness Sprint

This is a bounded, principal-led engagement for a health plan facing a defined regulatory or policy-driven change. It establishes an actionable view of what the organization must implement, what is affected, what is missing, and what leadership needs to decide.

The sprint does not replace legal interpretation, clinical policy ownership, solution architecture, or the delivery teams responsible for implementation. It turns approved requirements into a traceable execution model those owners can use.

### In the sprint, we determine

- what the relevant requirement obligates the organization to do;
- which business capabilities and operating outcomes are affected;
- which workflows, handoffs, channels, systems, integrations, data, controls, and vendors participate in the outcome;
- where the current state does not yet support the required behavior;
- which decisions, dependencies, and exceptions are preventing a complete implementation plan;
- who owns each gap and what acceptance criteria define closure; and
- what evidence can demonstrate readiness across the end-to-end operating path.

## The implementation chain

**Policy → Obligation → Capability → Workflow → System → Control → Owner → Evidence → Outcome**

The chain is not a reporting template. It is a way to ask whether an implementation claim can be traced from the source requirement to behavior that a plan can demonstrate.

For a prior-authorization change, an obligation may affect utilization management. The workflow runs from request intake through validation, review or routing, determination, notification, and downstream processing. The systems may include provider channels, an API layer, a UM platform, clinical rules, communication services, claims controls, reporting, and vendor services. Each link needs an accountable owner, explicit control behavior, and evidence that the end-to-end path works—including expected exceptions.

An API can be complete while the operating model is not. A workflow can be designed while a downstream claims or delegated-vendor dependency remains unresolved. A program can be reported green while nobody can produce the evidence that the intended population receives the intended behavior. The readiness sprint finds and structures those gaps before they become production defects or executive surprises.

## When this is useful

- A regulatory deadline has created multiple projects but no single readiness view.
- Compliance, operations, technology, product, and vendors have each interpreted the work differently.
- A prior-authorization, interoperability, reporting, or policy change looks technically on track but operationally unclear.
- Leadership needs an independent answer before declaring readiness, funding more work, or escalating a vendor.
- Testing is planned at the application level, but no one has defined the end-to-end operational scenarios and evidence that matter.

## What this is not

- Legal, clinical, actuarial, or regulatory advice.
- A replacement for accountable client executives, compliance owners, architects, or delivery teams.
- A generic PMO status report or a software implementation.
- A declaration of compliance or certification.

The result is a defensible implementation-readiness view and a bounded backlog that client teams and delivery partners can execute.
