You do not need to begin an AI project by choosing a model or proposing a custom application. Start with the work an operator is repeatedly reconstructing and the decision that work supports.

An off-the-shelf model may help prepare prose. It does not define the facts, authority, permissions, or action boundary around that prose.

## Choose a bounded task

A useful first candidate is preparing a client follow-up from recorded context, summarizing approved material, or proposing a structured work package for review. Identify the user, trigger, allowed sources, and output the reviewer needs.

A simpler workflow rule or an existing feature may solve the problem. Use it when the model would add uncertainty without useful assistance.

## Separate proposed content from facts

Keep the source information and open questions visible. A model can propose a summary; a responsible person confirms the factual interpretation before it enters an authoritative record or client communication.

Scores, rankings, workflow states, and approval rules remain governed by explicit deterministic logic. Do not make a confident draft responsible for deciding them.

## Design the unavailable path

The operator should still be able to inspect the context and proceed manually if a provider times out or the response is unusable. Record the attempt, classify the failure, and show what needs attention.

RachelOS demonstrates an audited wrapper and human review around AI-assisted outreach in an independent, single-operator system. The provider call is only one part of that implemented workflow.

## Measure the whole task

Count time preparing and reviewing, corrections, rejected drafts, unresolved information, completed actions, and failure recovery. A fast generation time can conceal expensive review. Compare the same kind of work before and after the change.
